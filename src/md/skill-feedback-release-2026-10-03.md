# Skill-specific feedback and private reminders

All twelve production skills now offer two optional observable cues and concrete anchors for ratings 3 and 5, in English and Norwegian. The existing 1–5 scale, rating source, and four checkpoints per twelve-item group round remain unchanged. These are original coaching references aligned with the app's skill focus, not a validated competency instrument or a copied scoring rubric.

## Experience

In separate-device groups with an active observer, **What to look for** appears only on that observer’s screen, during preparation, practice and checkpoints. Therapists, clients and watching participants receive no scoring reference. In a pair, the therapist gets it only at a checkpoint with practiced items, adapted for self-rating; the client continues giving feedback aloud. No scoring reference appears for an all-passed set.

Individual practice uses two skill-specific first-person reflection questions in the same collapsed reference, during practice and at rating. The observable anchors and 1–5 scale are shared with observer rating. Self-rating is labeled **Reflect on your attempt** and asks the therapist to consider their own choices, including the retry. On a shared device, observer guidance sits inside the observer’s role section. References start closed to keep phone screens brief.

The therapist can keep one optional **Next attempt** adjustment (up to 160 characters) per skill and language. It is editable in preparation and at a checkpoint, concise and read-only during items, and returns in a later session. A different case/difficulty for the same skill uses the same reminder. Changing/removing it does not change ratings. Copying to share is explicit on a personal device; there is no automatic room sharing.

On a shared device the reminder remains closed and is not fetched until opened deliberately. Opening it makes it visible on that screen. A saved note is not private from someone physically looking at the therapist's own device.

## Storage and failure behavior

Migration `20261003072701_private_practice_goals.sql` adds one table with owner-only select/insert/update/delete RLS. Room membership and permission to rate someone do not grant note access. The primary key covers the user foreign key and RLS filter. Account deletion cascades to notes. A private invoker trigger sets timestamps; no new public definer function is exposed.

Notes are not added to room snapshots, ratings, feedback reports, or general browser/session storage. Account changes clear the in-memory cache and displayed content, and delayed requests are discarded. Writes from editors in one page are serialized. Concurrent edits from different devices use the last database write; this is one current reminder, not a collaborative document or note history.

Read failure offers Retry before editing an unknown existing note. Save failure keeps the draft. Backend errors are generic so database constraint details containing a note cannot enter logs or the UI. This deliberately stores only a short practice adjustment, without transcripts or client/personal details.

## Editorial review still needed

Qualified EFT instructors and a native Norwegian reviewer should check the anchors and self-reflection questions before treating them as standardized instructional criteria. In particular, compare skill distinctions and how observers interpret 3 versus 5 on held-out fictional attempts. This implementation has not established inter-rater reliability, clinical benefit or an optimal rating interval.

Self-awareness anchors reward noticing, pausing, attention and boundaries. They explicitly allow private details to remain private. Other anchors assess the therapist's choices rather than the intensity of the client's emotion, willingness to disclose, or repetition of a model response.

The framing is consistent with EFT's attention to experiencing and therapeutic process, described by [ISEFT](https://www.iseft.org/What-is-EFT). That source supplies background, not validation of these original anchors. The data/privacy implementation follows [Supabase's RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).
